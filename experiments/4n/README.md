## Frozen 4M attribution
4M's scientific gates failed only on:
1. R4 recovery >=5/6 (actual 4/6),
2. >=8 manufactures (actual 6),
3. >=1 trace-confirmed recipe (actual 0).

The key forensic finding is that the benchmark ledger/cache recorded actually executed API requests that were not present in the `DocEvidence[]` handed to the trace compiler. Examples observed during the same run included API-shaped product and vehicle-decode requests. The 4M trace compiler only consumed document evidence that survived the crawl/evidence materialization boundary, so executed requests generated by later reference/spec acquisition could disappear before trace synthesis.

Therefore 4M did **not** falsify executed-request proof. It exposed a representation-boundary bug: executed GETs are not first-class evidence objects across acquisition stages.

A second gap: 4M implemented exact-build and same-family slot induction, but did not completely join an executed concrete example to an already documented placeholder/parameter role. This matters when the executed example value differs from the task build value.

## 4N hypothesis
Every safe GET actually executed during acquisition must immediately emit an immutable, first-class `ExecutedGetTrace` object. The operation compiler consumes this trace graph directly rather than trying to reconstruct executed requests from `DocEvidence` later.

```text
crawl / reference expansion / standard spec / embedded spec / documented example
                              ↓
                           safe GET
                              ↓
                    ExecutedGetTrace emitted
          ┌────────────────────────────────────┐
          │ provider/case lineage              │
          │ acquisition stage                  │
          │ parent evidence IDs                │
          │ requested URL                      │
          │ final URL                          │
          │ status/content type                │
          │ body fingerprint                   │
          │ optional structured scalar summary │
          └────────────────────────────────────┘
                              ↓
                    Executed Request Graph
                              ↓
  exact-value / trace-family / documented-role join
                              ↓
                   changed-input safe probe
                              ↓
       observed mapping → validator → live → replay
```

## First-class trace requirements
An `ExecutedGetTrace` MUST be created at the network/cache boundary, not reconstructed from a later document representation.

Required immutable fields:
- `trace_id`
- `case_id`
- `provider_candidate_id`
- `stage` in a closed enum such as `CRAWL`, `REFERENCE_EXPANSION`, `STANDARD_SPEC`, `EMBEDDED_SPEC`, `DOCUMENTED_EXAMPLE`
- `parent_evidence_ids`
- `requested_url`
- `final_url`
- `requested_at`
- `status/disposition`
- `content_type`
- `body_fingerprint`
- `body_bytes`
- cache/network origin metadata (`network` vs same-run cache reuse)

A cache hit emits a distinct provenance event/consumer trace that may share the same response fingerprint. Cache reuse must never erase the current case/provider lineage.

## Trace graph scope
For each synthesis attempt, the trace graph may consume only traces whose lineage is provably attributable to the current case/provider candidate or to evidence explicitly derived from that same provider candidate.

No trace from another candidate may be promoted merely because the host or URL shape matches.

## Three admissible slot proofs
4N implements exactly three provider-blind slot-proof routes.

### A. Exact task-build whole-value proof
The normalized task build value occurs exactly once as a whole path segment or whole query value in an eligible executed trace.

Substring-only or multiple occurrences reject.

### B. Executed trace-family proof
At least two eligible executed traces have:
- same method,
- same origin,
- same path segment count,
- same non-auth query-key set,
- exactly one whole path segment or query value varying,
- >=2 distinct values,
- task/entity/operation support.

### C. Executed example + documented role proof
An eligible executed concrete request is joined to a previously grounded documented operation/placeholder/parameter in the same evidence lineage.

Required join evidence:
- same preserved origin or a mechanically proven API-base relation;
- same normalized path/query structure after replacing exactly one documented parameter/placeholder with the concrete executed value;
- documented role is already accepted by the inherited graph using named parameter, placeholder or structural role evidence;
- task input maps to that role through existing provider-blind morphology/semantic correspondence;
- no other request text changes.

This proof is specifically intended to support cases where the documentation executes an example value different from the task build value.

## Executable-target negatives
The following cannot become execution targets merely because they contain `api` text:
- `/documentation/...`
- `/docs/...`
- `/reference/...`
- `/sdk/...`
- `/guide/...`
- `/help/...`
- OpenAPI/Swagger document files themselves
- static/image/font/script/media assets
- generic website/navigation pages

Such resources may contribute documentation/role context, but not become a trace target unless an independently grounded executable operation proves a different target URL.

A hard documentation/navigation negative overrides the presence of a later `/api/` segment in the same page path.

## Origin and request preservation
For trace-derived operations:
- origin is inherited from the executed trace or mechanically grounded API-base relation;
- validator must reject any origin drift;
- only the single proven variable value may be replaced;
- optional auth-like pairs may be removed surgically under inherited policy;
- all other path/query text remains identical;
- no reconstruction to a website root is allowed.

## First-class cache behavior
Keep 4M same-run acquisition/spec/probe caches.

The cache is not itself the trace graph. Each consumer request emits provenance even when response bytes come from cache.

Rules remain:
- exact normalized GET URL cache key;
- no persistence across benchmark runs;
- scope/safety check on every consumer, including cache hits;
- live verification is not served from acquisition/spec cache;
- replay remains zero external calls;
- duplicate actual network fetches for identical eligible URLs remain zero.
